# Archivist во внешней памяти

Многие пользуются долгосрочной памятью агентов: OpenViking, mem0 и другими. Archivist кладёт туда знания проекта, чтобы их видели и другие агенты и плагины, а не только Claude Code в этом репозитории. Этот документ описывает, как он это делает. Другой плагин может по нему находить, читать и не ломать записи Archivist.

## Принцип: журнал — истина, память — проекция

1. **Единица — запись.** Каждая действующая запись (команда, ловушка, решение, процедура) — один элемент памяти. Текст самодостаточен: его понимает агент, который ничего не знает об Archivist.
2. **Устойчивый ключ** `archivist/<проект>/<id записи>`.
   - Проект берётся из `git remote get-url origin`, сведённого к `host/owner/repo` (без учётных данных и порта), поэтому совпадает на всех машинах. Если remote нет — `local/<имя папки>`.
   - Где система памяти даёт выбрать адрес, ключ и есть адрес. Где она выдаёт свой id, адаптер ищет элемент по ключу перед добавлением, так что дублей не появляется.
3. **Подпись.** Последняя строка элемента: `Project: <проект> · Archivist <id> · updated <время>` (у решений ещё `ADR-NNNN`). По ней копия Archivist узнаёт свой элемент и видит, чья версия новее.
4. **Дословно.** Факт уже отобран, поэтому пишется без переписывания через LLM. Режимы «извлечения» (`remember`, `infer: true`) не используются.
5. **Сведение к журналу.** Одно пространство делят клоны, worktree, ветки и коллеги с общим сервером памяти, поэтому:
   - элемент пишется, когда изменилась своя запись, или когда эта копия видит запись впервые, а в памяти её нет или там версия старше;
   - более новую по `updated` версию Archivist никогда не перезаписывает;
   - удаляет только элементы записей, которые его журнал вывел из оборота, кто бы их ни писал;
   - пропавший элемент не восстанавливает, а сообщает о нём;
   - элементы, которых нет в его журнале, не трогает;
   - запись, у которой пропали доказательства (файлы), не пишет и не удаляет: они могли пропасть только в одной ветке;
   - если у одной записи в памяти оказалось несколько копий (новая версия добавилась, а старую удалить не вышло, или две копии проекта добавили её одновременно), оставляет самую свежую; при одинаковой дате предпочитает совпадающую с журналом, а лишние удаляет.
6. **Кэш и сверка.** Что отправлено из этой копии, лежит в `.archivist/.local/memory-<хранилище>.json`. Обычная синхронизация сравнивает журнал с кэшем и память не читает. С памятью она сверяется при старте сессии и когда кэш пуст (новый клон или worktree). Где чтение памяти тратит квоту (облако mem0), сверка при старте сессии идёт не чаще раза в сутки на проект; `/archivist memory sync` сверяет всегда.
7. **Своё пространство.** Писать и удалять Archivist может только свои подписанные элементы, а читать — всю память.
8. **Транспорт.** Archivist ходит в память либо через MCP-сервер уже подключённого плагина памяти, его соединением и ключами, либо через API системы с ключом из личных настроек плагина (`/config`).
9. **Чужое облако — только по согласию.** В память, которая хранит записи в чужом облаке (сейчас это облако mem0), уходят только проекты из личного списка. Пока проект не включён, туда не уходит ничего: ни записи, ни удаления, ни сверка, ни поисковые запросы.
10. **Чтение — подсказка, а не истина.** Память помогает не записывать то, что другие агенты уже знают, но в журнал из неё ничего не переносится само.
    - Перед курированием задачи Archivist один раз ищет в памяти по началу первого промпта (до 200 символов) и до пяти изменённых файлов проекта. Файлы вне проекта в запрос не попадают. В промпте маскируются длинные токены и значения рядом со словами вроде «пароль» или `token`: это защита от случайности, а не гарантия.
    - Куратор видит только общее: ресурсы OpenViking, общий канал проекта в mem0. Личная память ему не показывается.
    - Плагин памяти сам сохраняет текущую сессию, и Archivist не должен принять только что сохранённый факт за уже известный. OpenViking кладёт такое в личную память, которую куратор не читает. В mem0 захваченное лежит в том же канале, поэтому отбрасывается всё, что появилось или изменилось с начала задачи (`updated_at`, иначе `created_at`, не раньше её старта). `find` в OpenViking дат не отдаёт: ресурс, записанный руками прямо во время задачи, куратор увидит как уже известный.
    - Отбрасываются и записи, известные своему журналу, и элементы Archivist других проектов. Элемент своего проекта, которого нет в журнале, остаётся: его написала другая ветка или клон.
    - Из оставшегося куратор получает до восьми фактов: по одной строке до 300 символов, с замаскированными секретами. В промпте они стоят как справочные данные, а не инструкции. Пользоваться ими можно только чтобы не добавлять факт, который там уже есть, или подкрепить существующую запись.
    - Это проверяется и кодом: если куратору показывали факты, запись применяется сама, только когда её подтверждают заметки задачи, сигналы или записи журнала, которые он видел. Подтверждают — значит, там есть не меньше половины её основ слов и каждая команда в обратных кавычках дословно. Остальное уходит на ревью, и повторное появление такую запись не применяет. Правки и вывод из оборота проверяются так же.
    - Отчёт перечисляет показанные факты. Сбой поиска попадает в отчёт и анализу не мешает. На поиск даётся 20 секунд.
    - `/archivist recall` ищет шире: в OpenViking — личную память и ресурсы, в mem0 — общий и личный каналы. Записи своего журнала он не повторяет. Сначала идёт журнал, затем до пяти находок с указанием источника. `archivist recall` в терминале с памятью не работает.

## OpenViking

OpenViking подключается через MCP своего плагина.

- Адрес элемента: `viking://resources/archivist/<host>/<owner>/<repo>/<id>.md`.
- Запись — `write` (`mode: "replace"`), удаление — `forget`, список — `list`, чтение — `read`, поиск — `find` с `level: [2]`, чтобы вместо сводок по папкам приходили файлы: для куратора с `target_uri: "viking://resources/"`, для `recall` без него. Сервер перечисляет находки по видам, поэтому Archivist сортирует их по проценту совпадения сам.
- Recall плагина OpenViking показывает такие ресурсы аннотацией, полный текст агент дочитывает через `read`.

Элемент выглядит так:

```
# Mod code has no Node types

Gotcha: Typecheck it with `tsc -p tsconfig.mod.json`
Why: the mods runtime has no Node
Where: src/adapters/**

Project: github.com/owner/repo · Archivist gk-1a2b · updated 2026-10-23T10:00:00.000Z
```

## mem0

Archivist ходит в mem0 по REST со своим ключом и пишет текст дословно (`infer: false`). Облако это или свой сервер, решает адрес в `/config`: пустой адрес, хост `mem0.ai` или его поддомен — облако, любой другой — свой сервер mem0 (`server/` в репозитории mem0, запуск — `make bootstrap`).

**Скоуп** такой же, какой вычисляет плагин mem0 для Claude Code; у плагинов для Codex и Cursor та же логика. Поэтому recall этих плагинов в облаке находит записи Archivist.

- `app_id` — `MEM0_PROJECT_ID`, иначе `<owner>-<repo>` из `git config --get remote.origin.url`, иначе имя корневой папки репозитория.
- `agent_id` — `<app_id>-<первые 10 hex от sha256 нормализованного remote>`; без remote — `local-<app_id>-<первые 10 hex от sha256 пути корня репозитория>` (`git rev-parse --show-toplevel`, даже если сессия начата в подпапке).
- `user_id` — поле `user_id` плагина mem0 в `/config`, иначе `MEM0_CODE_USER_ID`, `MEM0_USER_ID`, `MEM0_RESOLVED_USER_ID`, `USER`, `USERNAME`, иначе `default`.

**Metadata** элемента плоская, потому что облако фильтрует только по ключам верхнего уровня: `archivist_key` (`archivist/<проект>/<id>`), `archivist_project`, `archivist_id`, `archivist_updated`. Подпись по-прежнему стоит и последней строкой текста.

| Операция | Облако (`https://api.mem0.ai`) | Свой сервер |
|---|---|---|
| записать | `POST /v3/memories/add/` с `infer: false`, `immutable: true`, `app_id`, `agent_id`, `user_id` | `POST /memories` с `infer: false`, `agent_id`, `user_id` |
| изменить | добавить новую версию, затем удалить старую: `immutable` запрещает `PUT` | `PUT /memories/{id}`, id не меняется |
| удалить | `DELETE /v1/memories/{id}/`; 404 — уже удалено | `DELETE /memories/{id}`; 404 — уже удалено |
| список проекта | `POST /v3/memories/` с фильтром по `app_id` и `metadata.archivist_project`, по 200 на страницу, вместе с текстом | `GET /memories?agent_id=…&top_k=1000`, свои элементы отбираются по `metadata.archivist_project` |
| поиск в общем канале | `POST /v3/memories/search/` с фильтром `{"AND": [{"agent_id": …}, {"app_id": …}]}` | `POST /search` с `filters: {"agent_id": …}` |
| поиск в обоих каналах | тот же запрос: `OR` общего канала и `{"AND": [{"user_id": …}, {"app_id": …}]}` | два запроса, `filters: {"agent_id": …}` и `filters: {"user_id": …}`; ответы сливаются по `score`, повторы убираются |
| авторизация | `Authorization: Token <ключ>` | `X-API-Key: <ключ>`; без ключа — без заголовка |

- **Дубль при изменении в облаке.** Новая версия добавляется раньше, чем удаляется старая. Если добавления упрутся в квоту, в памяти останется прежняя версия, а не пустое место. Цена: если старую удалить не вышло, какое-то время живут две копии, и ближайшая сверка убирает лишнюю.
- **Квота.** Список отдаёт текст, поэтому сверка не читает записи по одной: на проект уходит один запрос списка (несколько, если записей больше 200), и не чаще раза в сутки. Поиск идёт отдельно: один запрос на нетривиальную задачу и один на `/archivist recall`. Если квота кончилась, он не приостанавливается, как синхронизация, а падает в отчёт задачи.
- **Отказ.** Если mem0 не принял ключ или кончилась квота (HTTP 401, 402, 403, 429), прогон останавливается, а синхронизация ждёт следующего старта сессии или `/archivist memory sync`. Ключ не попадает ни в лог, ни в тексты ошибок.
- **Запрос, который mem0 не примет и при повторе:** любой другой ответ 4xx (например, требование своего LLM-ключа), ответ не в JSON или добавление, после которого ничего не сохранено. Остальные записи прогона всё равно уходят, а синхронизация после ходов ждёт следующего старта сессии или `/archivist memory sync`: так один и тот же запрос не повторяется на каждом ходу и не тратит квоту. Ошибки сети и 5xx повторяются при следующей синхронизации, как раньше.
- **Свой сервер** отдаёт за раз не больше 1000 элементов: если пришло ровно столько, health предупреждает, что список мог обрезаться. Id агента или пользователя он требует на верхнем уровне `filters`, поэтому один запрос с `OR` здесь не проходит. Эмбеддинги он считает через OpenAI или Gemini, так что текст записей и поисковых запросов уходит и туда. Плагины mem0 со своим сервером не работают: они ходят только по путям облачного API.

## Другие системы памяти

Адаптер — это небольшое соответствие операций Archivist операциям системы. Если система чего-то не умеет, Archivist этот шаг пропускает.

| Система | Как подключается | Статус |
|---|---|---|
| OpenViking | MCP подключённого плагина, адрес элемента — наш ключ | сделано |
| mem0, облако и свой сервер | REST со своим ключом, ключ — в `metadata.archivist_key` | сделано |
| Hindsight | REST или MCP банка `coding-agent::<проект>`, `document_id` — наш ключ; recall плагинов видит только извлечённые факты | следующий раунд |
| supermemory | REST v5, `id` документа — наш ключ, подпись — в metadata: текст возвращается не байт в байт | следующий раунд |
| basic-memory | MCP, путь заметки — наш ключ | потом |
| MemPalace | MCP, поиск и удаление по `source_file` | потом |
| claude-mem, Serena; Zep, Cognee, Graphiti, MemOS, Memori | — | не планируются: в claude-mem нельзя задать свой ключ и удалить запись, Serena пишет внутрь репозитория, остальные хранят только извлечённые факты |

## Настройки и команды

```json
"memory": { "enabled": true, "project": "auto" },
"rules": { "files": true }
```

- `memory.enabled` — синхронизировать с памятью, выбранной в `/config`, и читать из неё; `false` выключает и то и другое для проекта, что бы там ни было выбрано.
- `memory.project` — `auto` или своё имя проекта.
- `rules.files: false` — не создавать файлы правил и skills для Claude Code, знания идут только в память. `INDEX.md` и ADR остаются.
- В `/config`, в личных настройках плагина: какая память (`auto`, `openviking`, `mem0`, `off`), адрес и ключ mem0, проекты для облака.
- `/archivist memory` — куда идут записи и что с ними. `/archivist memory sync` — сверить сейчас. `/archivist memory clear` — убрать свои элементы проекта из памяти. `/archivist memory on` и `off` — отправлять ли этот проект в облачную память.

Выключение синхронизации, `off`, смена системы памяти и `archivist uninstall` из памяти ничего не удаляют: удаление там необратимо, поэтому оно делается только явной командой `clear`. Она работает и для проекта, который в облако больше не отправляется.
